## Status and Program of Record

This file is the working draft of {% include term.html id="qnir" text="QnIR" %} v0.3 — the intermediate-representation layer of the Qn definition taxonomy, positioned between the {% include term.html id="qnlang" text="QnLang" %} surface language (whose expressions collapse deterministically to concrete values at compilation time, `docs/abstractionLayers.md` §6.3) and the execution substrate. The layer's declared role is fixed by the committed glossary definition of `docs/_data/glossary/primitives.yml` and is unchanged by this draft: intermediate representation for hardware abstraction, bound enforcement, and deterministic execution without exposing floating-point semantics. The file status is **DRAFT**: QnIR remains **[PENDING]** in the portal milestone diagram (`docs/index.md`), and canon entry is gated exclusively by the promotion criterion quoted below. Every artifact in this file carries the tag **[v0.3.0-draft.5 — DRAFT]** for new declarations, with the committed declarations of v0.3.0-draft.1 through v0.3.0-draft.4 standing as committed except where a Loop-3 repair wave explicitly withdraws a wording (each withdrawal itemized, with the withdrawn bytes preserved verbatim, in the Wave record of the wave that made it) and the claimed validity of the record is internal consistency within declared finite boundaries under {% include term.html id="computational-consistency" %}.

The governing instrument of the entire draft is the Loop-2 adversarial review of the QnIR v0.2 candidate (verdict preserved verbatim: "major revision; do not promote QnIR v0.2 to the canon"), whose required repair sequence is preserved verbatim below. The sequence's own preamble — "The order matters because later artifacts inherit earlier definitions." — and the review's milestone framing are preserved verbatim from the scope-and-verdict section:

> The appropriate v0.3 milestone is therefore a small, executable core with a formal transition relation and differential tests. Geometric products, containers, calls, fork–join, and STARK proving should remain profile-gated extensions until each has a specified state transition, cost bound, and validator. The draft's narrow "no implementation, no superiority, no closure" disclaimer is accurate and should remain.

## 1. The Frozen Minimal Core (Repair Step 1)

### 1.1 Freeze Statement and Closure Rule

The operative instruction of this section is the Step-1 row of the repair sequence, preserved verbatim: action — "Freeze a minimal core"; acceptance condition — "Constants, tuples, exact arithmetic, comparison, bounded structured control, status, commit, witness, and halt. Move calls, saturation, containers, fork–join, and road proofs to extensions." The freeze is executed here as a **closed inventory at construct-family level** (§1.2), an **explicit deferral register** (§1.3), and a **constraints-inherited register** (§1.4). The reviewer's conclusion states the intent this freeze implements: "The next iteration should reduce scope, define the core relation exactly, and make every example mechanically checkable."

The closure rule is default-deny under the {% include term.html id="no-implicit-rule" text="No Implicit Rule" %} discipline: **any construct not listed in §1.2 is out of the core**, and any construct listed in §1.3 is out of the core even if a v0.2 opcode table carried it. A construct enters or leaves the inventory only by an amendment to the repair sequence, adjudicated under the {% include term.html id="boc-policy" text="BOC policy" %} with the Loop-2 transcript as the binding constraint source. The freeze states **boundaries, not semantics**: per-construct state transitions, encodings, token lifecycle algebra, and failure behavior are Step-2 deliverables and are deliberately not pre-empted here. Where a §1.2 row names a semantic obligation, it records the obligation's owner step; it does not discharge it.

### 1.4 Constraints-Inherited Register

The register below records every review finding that binds the frozen core, with the discharge step that owns it. A constraint is *inherited*, not discharged, by this freeze: the freeze shapes the inventory so that each constraint has a discharge path, and no inventory row may be read as resolving a semantics question that belongs to a later step. Work quantities in the bindings are measured in the {% include term.html id="compute-unit-u" text="Abstract Compute Unit U" %} under the declared envelopes of the {% include term.html id="simemp" text="SIMEMP" %} constraints (`docs/simemp.md` §4.4).

| Constraint | Source and grade | Binding on the frozen core | Discharge step |
|---|---|---|---|

### 2.1 The Determinism Statement

The determinism claim of this section is stated exactly as the acceptance condition requires:

> **`Eval(Intent, D, V) = Execution`** — for every well-formed triple `(Intent, D, V)`, evaluation yields exactly one execution.

The triple is bound as follows. **Intent** is the program artifact: the typed block graph with its block-argument signature (§2.4), the instruction sequence of each block over the nine frozen families, the declared type bound of every value, the declared fallback edge of every lookup (§2.5), the extension side table for non-uniform per-instruction attributes (§2.6), and the profile reference carrying the declared trip/depth ceilings and type-bound parameters. Intent is *well-formed* iff it satisfies the static legality rules of §2.3–§2.6: only core-family instructions; an arity-closed, consistently typed block-argument graph; every value carrying a declared type with a declared bound; every lookup carrying its declared fallback edge; every flag combination known and every `EXT` side-table reference resolving; and a profile reference present, since ceilings and bounds are profile parameters (Obj 2). A program that mentions a deferred family, carries an unknown flag combination, or cites a nonexistent side-table record is not a legal Intent and has no semantics — rejection is static, at Intent formation. **D** is the dependency environment: the content-addressed input environment (constant-table entries and input values, each cited by content address) that execution may read, under {% include term.html id="dependencies-determinism" text="dependencies determinism" %}; execution reads no input that Intent does not declare. **V** is the explicit version tuple `(semantics version, encoding version, profile version)`: the semantics version is this file's version — v0.3.0-draft.5 pins the transition relation, the instruction-level closure, the lifecycle algebra, and the total terminalization function of this §2; the encoding version pins the layout of §2.6; the profile version pins the declared ceilings and bounds that ride Intent. Versions are part of the determinism claim, not metadata about it: a change to any component of `V` is a different `Eval`, and the transition record of §2.6 binds all three into every committed transition.

**Execution** is the maximal transition sequence from the initial configuration under the relation of §2.3, together with the complete ordered list of transition records and the terminal configuration. The initial configuration is declared, not computed: entry block with its arguments bound from `D`, the declared initial status pool (empty unless the Intent declares entries — the conformance birth path of §2.5, at most one token per declared type) and receipt queue, zero accumulators, zero clock, step index 0, state running, version bindings `V`. The semantics makes no universal termination claim: bounded loops carry declared ceilings, but whether a given Intent terminates within them — and how budget admission certifies that statically — is the Step-3 deliverable (F4). The claim this section makes is weaker and exact: *if* a well-formed triple's evaluation reaches halt, the halt is reached by exactly one transition sequence, and that sequence is fully recorded.

**The condition grammar.** The declared condition codes are the closed set {`LT`, `LE`, `EQ`, `NE`, `GT`, `GE`}, evaluated over the comparison-domain value r ∈ {−1, 0, 1} by the declared total predicates: `LT`: r = −1; `LE`: r ≤ 0; `EQ`: r = 0; `NE`: r ≠ 0; `GT`: r = 1; `GE`: r ≥ 0. Every code decides on every result — the grammar is total, closed, and deterministic, and an `OBS` result (bound [0, 1]) is a legal comparison-domain value, so a branch can test token presence (its `NE` code) without any new opcode.

**The zoom normalizer and the zoom-boundary comparison (executable functions).** A zoom-carrying value is a declared value form: a pair (m, z) of an exact integer mantissa and an integer zoom exponent, each within the pair's declared ranges; the pair denotes the exact dyadic quantity m·2^z, and a program declaring no zoom ranges contains no zoom-carrying values, with every rule above unchanged on it. No floating point exists anywhere in the relation. The **minimal-zoom normalizer** is the executable function N: N(0, z) = (0, 0) — the canonical zero of §2.6; for m ≠ 0, write m = 2^k·q with q odd (k the exponent of 2 in m), and N(m, z) = (q, z + k) — the unique odd-mantissa form of the dyadic, so the normalizer's minimal representation is unique by the uniqueness of the odd-mantissa decomposition of a dyadic rational (the demonstration obligation that §2.2 and `QO-24` carry to the promotion artifacts stands, now over a declared function instead of a name). The **zoom-boundary comparison** is the executable predicate the `CMP` rule applies under N: two values are equal exactly when their normalized pairs are equal; otherwise, for normalized (q₁, z₁) and (q₂, z₂) with z₁ ≤ z₂, the ordering is decided by comparing q₁ against q₂·2^(z₂−z₁) in exact integer arithmetic — the exponent difference is non-negative, so the shift is exact and the comparison never rounds. A zoom exponent outside its declared range is the `CMP` pre-dispatch rejection above; there is no boundary behavior beyond the declared rejections — behavior at declared zoom boundaries is part of the declared function exactly here.

**The tuple field structure.** A tuple value carries its declared signature: the field count k and the declared type and bound of each field, both static instruction data; the canonical encoding of §2.6 encodes the fields in declared order over the components' canonical encodings (the complete byte grammar is R2's — the semantic structure is fixed here). Field identity is positional under the declared signature; there is no field-name resolution, no header-only comparison (F6), and no default field.

**Derived counters (no configuration change).** The trip count of a static back-edge site is the number of its prior traversals in this execution, derived canonically from the committed record sequence — each traversal is visible in the record's PC field — and the nesting depth at a block entry is derived from the same sequence. The ceiling preconditions of `BR` and `JMP` compare these derived counts against the declared ceilings; no component is added to the configuration tuple of §2.2, which stands as committed, and an implementation may maintain the counts incrementally under the obligation that the maintained value equals the derived one at every step.

### 2.4 Block Arguments and Dynamic Instances (F3 Discharged)

Control is frozen as basic blocks with explicit block arguments, and the dynamics make the v0.2 defect impossible by construction. Every edge of the block graph — forward, branch, and back-edge — supplies operand values for exactly the target block's declared arguments, and entering a block mints a fresh instance id for each of its arguments. Loop headers therefore take their per-iteration state as block arguments, and a back-edge operand **may occur later in the static instruction order than the branch that cites it**: the operand is resolved when the edge executes, at block entry, not at static scan. This is precisely the named defect of F3 — "loop headers need block arguments whose back-edge operands may occur later statically" — discharged as a static well-formedness rule (the block-argument graph is arity-closed: every edge supplies the target's arity, typed consistently) plus an entry-time resolution rule (§2.3, control row).

Within a block, each instruction that defines a value binds it in the current instance context, so one value per static instruction is a statement about *names* — the pair `(static value id, instance id)` — and never about storage slots: per-iteration redefinition mints a new instance instead of overwriting an old one. Instance ids are minted in transition order, are execution-scoped, and are never reused within an execution, which makes the dynamic value store's canonical encoding (§2.6) well-defined at every step. The store is the abstract semantic state; what a profile does with it — liveness windows, register allocation, spilling under `QO-18` — is realization, not semantics: no capacity constant of any profile is a validity limit of this relation (Obj 2).

### 2.5 The Token Lifecycle Algebra and Failure Behavior (Obj 5 / `QO-22` Discharged)

The review's verdict on `QO-22` is preserved as the design constraint: "The two-tier token idea is sound; the v0.2 partition and mappings are not." This section therefore declares the v0.3 partition, the lifecycle verbs over it, and the failure behavior of the core, with no silent mapping anywhere.

**The two tiers.** **Tier O — operational tokens** are recoverable by specified fallback behavior and carry no semantic verdict. Declared member: `STATUS_LOOKUP_MISS` — operational control flow, consumed by the declared recompute fallback: the fallback edge is declared in Intent (§2.1), a lookup miss routes control to that edge's target, and the token is consumed only when that fallback entry completes successfully — the fallback block completes, births no token, and ends in no typed rejection; a fallback that misses again leaves the earlier token outstanding and births a fresh miss token with its own birth site, and every birth and consumption is traced (Loop-3 F12 repair, v0.3.0-draft.5 — a miss token is never consumed by an unsuccessful fallback). **Tier S — semantic tokens** are outcomes that propagate to the exit unless the program explicitly consumes or promotes them. **Lifecycle verbs.** Birth (typed, sited at `(step index, position)`), observation (a typed predicate that reads a token's presence and consumes nothing), consumption (only by a successful Tier O fallback completion or by the declared `PROMOTE` instruction — the two consume paths of the closed vocabulary, per the terminalization function below), propagation (unconsumed tokens ride the pool across transitions unchanged), and terminalization (at halt, every outstanding token terminalizes and is recorded in the terminal receipt — unresolved semantic debt at every exit is surfaced, never discarded, which is the family-9 scope boundary of §1.2). The `QO-22` test list — success-after-recovery, unresolved debt at every exit, multiple outstanding tokens — passes to Step 4 as the conformance suite's input, unchanged.

**Failure behavior and the total terminalization function (F12 repaired, [v0.3.0-draft.5 — DRAFT]).** A typed rejection is fatal: the machine cannot proceed past a rejected instruction, the transition that births the fatal token is the final transition, and the fatal state is sealed in that transition's own record — a later halt instruction cannot re-seal it (F7). The rule is replaced by a **total terminalization function** T, defined for every exit event and every configuration, over two closed vocabularies. **The closed terminal outcome vocabulary** (enumerated, closed — no other terminal outcome exists, and no outcome is reachable that the vocabulary does not name): `SUCCESS`; `NO_SOLUTION`; `EXPRESSION_TOO_COMPLEX`; `DOMAIN_ERROR`. Tier S — `STATUS_NEG_EVEN_ROOT` (birth: the declared initial status pool, and extension birth sites at Step 6; consume: the valid `PROMOTE`), `EXPRESSION_TOO_COMPLEX` (birth: the typed rejections of §2.3 and the §3.4 backstop and refusal; no consume path), `STATUS_DOMAIN_ERROR` (birth: the zero-divisor rejections of §2.3; no consume path). **The function.** T is defined over the three exit events, and is total. Exactly one outcome is produced at every exit, and every tie-break is declared: determinism by construction, not by silence. **The declared initial status pool.** The initial configuration of §2.1 carries the declared initial status pool: empty unless the Intent declares entries, at most one token per declared type, each entry a declared Tier S token with birth site (0, 0) — the conformance birth path that makes every terminalization combination of the §4.4 vectors buildable inside the frozen core (F12's "vectors for every combination"), with no extension admitted and no birth rule invented. **The frame parameter** is a derived execution parameter, not a configuration component: `real` for every configuration whose committed record prefix contains no `PROMOTE` transition, `wider` afterwards — determinism and executability follow from the record, and §2.2 stands as committed; the wider-frame rule's in-core content is exactly the `PROMOTE` semantics of §2.3, and the extended value semantics of the wider frame is the Step-6 extension surface, not pre-empted here. ### 2.7 The Fixed-Width/Exact Reconciliation (Named Obligation Discharged)

The declared stance of this semantics version is **exact value semantics over a fixed-width transport**:

1. **Values are exact.** Integer values are exact integers of unbounded range at the semantic layer; no operation wraps, saturates, or truncates, and no value is ever silently mapped (Obj 5).
2. **The transport is fixed-width.** The 64-bit word is the unit of encoding, dispatch, and commitment (`QO-30` preserved); an exact value occupies a minimal-length word sequence (§2.6), so the machine is exactly the "small, fixed-width deterministic machine" of §6.3 — fixed in its word format, not in a value-width limit.

The alternative stance — fixed-width 64-bit value semantics with typed overflow — was rejected on the register's own grounds: it would make a 64-bit capacity constant a core validity limit, which Obj 2 forbids in the absence of evidence, whereas the exact-over-transport stance requires no capacity constant at all. ### 3.1 The Ledger Equation (F2 Discharged)

An execution's transitions divide into **completed transitions**, which take their declared effects and post their declared charge, and **rejection transitions**, which post nothing, birth the fatal token, and are final (§2.5); the ledger bills the completed ones. The ledger of an execution `E` with completed transitions `t = 1 … n` is the single equation the acceptance condition requires:

> **`Work(E) = Σ_t charge(t)`** — the sum, over every completed transition of the execution, of that transition's declared charge.

Every quantity in the equation is measured in the {% include term.html id="compute-unit-u" text="Abstract Compute Unit U" %} under the declared envelopes of the {% include term.html id="simemp" text="SIMEMP" %} constraints, exactly as §1.4 and §2.2 fix the unit. **The charge of a transition is one declared quantity, and it is total for that transition.** Each rule of the §2.3 table declares the charge of its firing as a single function (§3.2) that already includes the base dispatch quantity — the `c_base + C_op` unification the F2 row of §1.4 requires, stated over families rather than opcodes: there is no separate dispatch deduction anywhere in the core, so the v0.2 defect that billed the base inside both a stage-1 deduction and a stage-2 reservation is excluded by construction. The equation's charge domain is closed over the four charge classes the F4 row names: the **gateway charge** — the declared fixed admission quantity `g(Intent)`, posted by the execution's first completed transition ahead of that transition's own rule charge; the **branch charge** — the declared charges of the control-family rules, in the core; and the **frame charge** and **proof-verification charge** — named in scope here, specified with their owning extensions (calls, Step 6; witness realizations, Steps 5–6) before any retention, riding this same equation and these same verbs without redefinition. The first completed transition's charged field therefore carries `g(Intent)` plus its own rule charge as one posted quantity; the itemization of the components is the terminal receipt's (§3.4), not a second field.

The ledger is a derived record, not new state: it is reconstructed from artifacts that §2 already commits — the transition records' charged and refunded fields (§2.6) in execution order, plus the terminal receipt's itemization — so equal executions have byte-equal ledgers, and the differential execution of Step 4 can check a ledger against its records mechanically. The per-class ledger traces that the F2 row of §1.4 requires to be published alongside the equation are conformance artifacts: the equation is fixed here so that the Step-4 oracle's one-trace-per-rule-class publications are mechanically checkable against it; the shape is a Step-3 deliverable, the publication a Step-4 one, and the distinction is recorded in §3.6 rather than left silent.

### 3.2 Static Operand Bounds as the Cost Domain (F1 Discharged)

The F1 row of §1.4 binds the core to cost parameters that are "declared immediates, header bounds, or static type bounds" and forbids any runtime quantity — `h1`, `h2`, `B`, `M`, `K` — from a core cost formula; its discharge step reads "Step 3 (with Step 2 typing)", because §2 already froze the typing: every value carries a declared type with a declared bound (§2.1), bounds are profile parameters (§2.7), and exceedance is rejected before dispatch (§2.3, §2.5). This section completes the discharge by fixing the **cost domain**: the charge function of every rule takes its arguments from declared immediates, declared header fields, and the declared static type bounds of the instruction's operands — all fixed at Intent formation — and from nothing else.

Three consequences are stated because they are the discipline, not decoration. First, no runtime quantity is metered: the actual encoded length of a runtime value, its magnitude, its representation, and its position in the store never enter a charge function; the dense/sparse load-time status that F1 named as representation-dependent has no core analogue at all, because the core has exactly one canonical value encoding (§2.6) and one cost per rule. Second, the declared charge upper-bounds the transition's actual work: an actual value occupies at most its declared bound of transport words (§2.6, §2.7), so a charge computed over declared bounds never under-bills what the transition moves — this is the direction of error a budget can tolerate, and it is the direction the discipline fixes. Third, charges are site-stable: the operands' declared bounds are per-static-instruction data, so one static instruction charges the same quantity in every instance and every iteration — dynamic instances (§2.4) change the values, never the cost. Every declared charge is positive — at minimum the declared base quantity, itself a profile parameter — which is what makes the fuel arithmetic of §3.4 strictly decreasing and the termination certification of §3.5 possible. Charge coefficients are profile parameters riding the profile version of `V`; the equation and the cost domain are core, the numbers are profile data, and `QO-23`'s governance clause over coefficient ranges lands with those declarations, not in this file.

### 3.3 Reserve, Charge, and Refund as Typed Ledger Movements

§2.2 declared the three work accumulators — charged, reserved, and refunded to date, as plain accumulators — and deferred their algebra to this section. The algebra is the settlement discipline of the review's own gateway schedule (`QO-23`): *reserve* the declared envelope, *charge* the metered work, *refund* the residue — declared here as movements of typed state, each with one declared site, no silent ordering.

**Reserve.** A reserve is an authorization against the declared budget. The execution's reserve is opened once, by the execution's first completed transition, which checks the declared admission bound `B(P)` of §3.4 against the budget and reserves it as an outstanding escrow. A rule may also declare a transition-local reserve `r(t) ≥ charge(t)` — its declared worst-case envelope for that firing — checked against the outstanding escrow before any effect posts. **Charge.** A charge posts against the outstanding escrow: the gateway charge and each completed transition's declared charge reduce the escrow and raise the charged accumulator. **Refund.** A refund releases unspent reserve: a transition-local reserve settles within its own transition (`refund(t) = r(t) − charge(t)`), and the escrow's outstanding remainder — the residue — is settled once, by the execution's final transition, halt or fatal rejection alike, whatever that transition's own posting status: pricing is outcome-independent by declaration, per `QO-23`'s own rule that payment must not depend on whether validation succeeds.

The invariants are total, and they are the acceptance condition's "reserve/charge/refund invariants": every reserve is non-negative and checked before it is honored; every charge satisfies `0 ≤ charge(t) ≤ r(t)` against the escrow that covers it; every refund satisfies `refund ≤ reserve outstanding`; the escrow never goes negative and the budget balance — the declared budget minus charged plus refunded — never goes negative; a reserve is settled either within its own transition or by the declared terminal settlement, so no reserve outlives the execution; and every movement posts into the transition record of its own transition (§2.6), whose pre/post state roots commit the accumulators (§2.2). The core's instantiation is deliberately degenerate and is stated rather than hidden: every core rule's charge is site-stable (§3.2), so every transition-local reserve equals its charge and every transition-local refund is zero — the non-trivial reserve/refund cycle of the core is the admission escrow and its terminal residue. The general shape is declared now so that the extension charge classes of §3.1 — frame escrows across calls, verification fees — inherit these exact verbs at their owning steps instead of redefining them. No family's transition semantics reads an accumulator: the accounting gates firing (§3.4) and is committed (§2.6), but the nine families' rules are unchanged — the ledger observes and gates the execution; it does not steer it.

### 3.4 Sound Control-Flow Budget Admission (F4 Discharged)

The F4 row of §1.4 requires admission to use "a maximum over bounded control-flow paths with declared trip/depth ceilings, or a dynamic fuel bound", excludes the claim that a simple per-instruction sum certifies admission, and requires gateway, frame, branch, and proof-verification charges in the ledger's scope. This section takes both arms of the review's "or", because each covers exactly the gap the other leaves: the static bound certifies, the fuel bound enforces.

**The admission bound.** For a well-formed Intent `P`, the declared admission bound is `B(P) = g(P) + max_π Σ charge(i) for i on π` — the gateway charge plus the maximum, over every control-flow path `π` from the entry block to an exit that respects the declared trip ceilings on back-edges and the declared depth ceilings on nesting, of the summed site-stable charges (§3.2) of the transitions the path executes. The boundedness of the paths is the same declared boundedness the core enforces at runtime: a loop back-edge cannot exceed its declared trip ceiling and nesting cannot exceed its declared depth ceiling without the typed rejection §2.5 already declares, so every executable path is a bounded path — which is the soundness direction admission needs. **The admission rule.** An Intent is admitted against the declared budget `W_budget` exactly when `W_budget ≥ B(P)`; the check's arguments are static — the budget, the ceilings, the bounds, and the charges are all declared quantities riding the Intent and its profile — and the check executes at the execution's first attempted transition, before any effect posts; on a pass, the transition completes normally and opens the escrow of §3.3. **The refusal.** A failed admission is a typed rejection in the sense of §2.5 — pre-dispatch, typed, sited — and its birth is `EXPRESSION_TOO_COMPLEX`, the resource/representation-limit token that section already declares: the declared budget is a declared resource envelope exactly as a declared bound is, and exhausting it is the same class of event. The refusal execution is the single rejection transition, the ledger closes at zero postings, and the terminal receipt itemizes the denial — declared budget against admission bound — under the itemization discipline of `QO-23`; whether a gateway profile prices refused admissions at all is a fee-policy parameter under that same clause, not a core rule.

**The fuel bound.** After admission, the outstanding escrow of §3.3 enforces the budget dynamically: a transition fires only if its declared reserve is covered, and the fuel arithmetic is strictly decreasing (every completed transition bills at least the declared base, §3.2), so the machine stops — fatally, with the same token, itemized — rather than over-burning silently. For an exactly-admitted Intent the backstop is provably unfirable: the actual path is one of the bounded paths over which the maximum was taken, so the actual total never exceeds `B(P) ≤ W_budget`. It is declared anyway, and its role is declared with it: a validator-side surrogate that computes `B(P)` may over-approximate — the safe error direction is false rejection, never false admission — and an under-approximating surrogate is caught by the backstop at run time instead of producing a silent over-burn. **What is not claimed.** The specification defines `B(P)`; it declares no algorithm for computing it. Naive path enumeration is exponential (F4's own finding), so the computational surrogate — and the polynomial-time question the review's `QO-17` places in its calibration chain, which orders "Correct F1–F4 before calibration" — is a Step-4 oracle deliverable with its own adversarial tests (the "budget boundaries" of the map's Step-4 row). **The termination certification.** §2.1 made no universal termination claim and named the question as this step's deliverable; the answer is now declared: every execution of a well-formed triple is finite. A program either completes transitions — each strictly consuming fuel against a finite budget — or is stopped by a typed rejection, including the fuel backstop; halting, fatal rejection, and fuel exhaustion are the only exits, and each is reached in finitely many transitions. This is a resource-bounded termination statement derived from the declared charges, not a halt-correctness claim, and it discharges exactly the certification §2.1 deferred.

### 3.5 Soundness of the Accounting

The accounting's soundness is one argument with four declared faces, each tied to a register item rather than to taste.

**Never under-billed.** Every completed transition's declared charge upper-bounds its actual work (§3.2), so `Work(E)` is an upper envelope of the execution's actual work in the {% include term.html id="compute-unit-u" text="Abstract Compute Unit U" %} under the declared envelopes of the {% include term.html id="simemp" text="SIMEMP" %} constraints; a budget that covers `Work(E)` covers the execution. **Never over-admitted.** Admission takes a maximum over the same bounded paths the runtime can execute (§3.4), so an admitted execution's total charge is at most `B(P) ≤ W_budget` — the static certification and the dynamic escrow are two views of one quantity. **Never silent.** Every movement posts into a committed record (§2.6), the terminal receipt itemizes the closed ledger (§3.4), and the refusal case is itemized too; there is no exit from an execution that does not state its own accounting. **Never a capacity constant.** The only finiteness limits anywhere in the relation are declared ones — per-value type bounds, trip/depth ceilings, and the declared budget — all profile parameters riding `V`; the accounting adds no core validity limit, which is the same Obj 2 discipline §2.7 declared for values, extended to executions: finiteness enters only by declaration.

Two closure statements follow. First, the ledger is deterministic: every movement is a declared function of static data and the fired rule, so equal executions have byte-equal ledgers, reconstructible from committed artifacts alone (§3.1) — which is what makes the promotion criterion's "independent differential execution" checkable over the ledger, not only over states. Second, the accounting is consistent with the fixed-width/exact stance of §2.7 rather than parallel to it: exact values over a fixed-width transport, exact work over a declared budget — in both cases the semantics is unbounded only where the text says it is, and finite everywhere else by declaration. This is the validity this section claims: internal consistency within declared finite boundaries, under {% include term.html id="computational-consistency" text="computational consistency" %} — no more, and deliberately no less.

### 4.1 The Differential Protocol

The protocol is the promotion criterion's "independent differential execution" made operational. Two implementations of the transition relation of §2.3 — the **reference interpreter** and the **second implementation** — execute the same encoded Intent under the same declared version tuple `V` (§2.1), and their outputs are compared byte-for-byte. Independence is declared, not aspired to: both implementations are separate codebases built from the committed bytes of §1–§3 and the normative requirements of this section and from nothing else — no shared code, no shared derivation, and no common input beyond this file's committed text and the declared vector format of §4.4. Conformance is decided by byte-equality of outputs, never by code review: an implementation whose outputs agree byte-for-byte is conformant, and one whose outputs do not is not, regardless of how its code reads.

The agreement surface is exact, and every point on it is a committed artifact of §2 or §3: (1) the canonical value encodings of §2.6; (2) the complete ordered transition-record sequence, each record carrying the F5 field list under the domain-separated encoding of §2.6; (3) the pre/post state roots at every step, computed by the state-root function under the declared encoding version (§4.3); (4) the terminal {% include term.html id="receipt" text="receipt" %} with its token itemization under the total terminalization function of §2.5; and (5) the reconstructed ledger of §3.1. A disagreement at any point is a conformance failure — registered as such, with the vector id and the disagreeing point named — regardless of which implementation is at fault; the protocol adjudicates the disagreement, never the implementation. The ledger check is mechanical by construction: §3.1 declared the ledger a derived record, reconstructed from the transition records' charged and refunded fields plus the terminal receipt's itemization, so the check that a published ledger equals the reconstruction of its own records involves no independent arithmetic anywhere — equal executions have byte-equal ledgers, and the oracle verifies exactly that. Every agreement point is a named check producing a typed verdict in the sense of §2.5 — pre-declared, sited, drawn from the declared vocabulary — and the protocol introduces no new status semantics of its own.

### 4.2 The Normative Assembler and Validator (F7, Step-4 Share)
