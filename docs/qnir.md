## Status and Program of Record

This file is the working draft of {% include term.html id="qnir" text="QnIR" %} v0.3 — the intermediate-representation layer of the Qn definition taxonomy, positioned between the {% include term.html id="qnlang" text="QnLang" %} surface language (whose expressions collapse deterministically to concrete values at compilation time, `docs/abstractionLayers.md` §6.3) and the execution substrate. The layer's declared role is fixed by the committed glossary definition of `docs/_data/glossary/primitives.yml` and is unchanged by this draft: intermediate representation for hardware abstraction, bound enforcement, and deterministic execution without exposing floating-point semantics. The file status is **DRAFT**: QnIR remains **[PENDING]** in the portal milestone diagram (`docs/index.md`), and canon entry is gated exclusively by the promotion criterion quoted below. Every artifact in this file carries the tag **[v0.3.0-draft.2 — DRAFT]** and the claimed validity of the record is internal consistency within declared finite boundaries under {% include term.html id="computational-consistency" %}.

The governing instrument of the entire draft is the Loop-2 adversarial review of the QnIR v0.2 candidate (verdict preserved verbatim: "major revision; do not promote QnIR v0.2 to the canon"), whose required repair sequence is preserved verbatim below. The sequence's own preamble — "The order matters because later artifacts inherit earlier definitions." — and the review's milestone framing are preserved verbatim from the scope-and-verdict section:

> The appropriate v0.3 milestone is therefore a small, executable core with a formal transition relation and differential tests. Geometric products, containers, calls, fork–join, and STARK proving should remain profile-gated extensions until each has a specified state transition, cost bound, and validator. The draft's narrow "no implementation, no superiority, no closure" disclaimer is accurate and should remain.

**Required v0.3 repair sequence** (preserved verbatim from [`docs/AiReviews/AiReviewQnIRv0.2.md`](https://github.com/cdqn5249/cdqn/blob/main/docs/AiReviews/AiReviewQnIRv0.2.md) §5):

## 1. The Frozen Minimal Core (Repair Step 1)

### 1.1 Freeze Statement and Closure Rule

The operative instruction of this section is the Step-1 row of the repair sequence, preserved verbatim: action — "Freeze a minimal core"; acceptance condition — "Constants, tuples, exact arithmetic, comparison, bounded structured control, status, commit, witness, and halt. Move calls, saturation, containers, fork–join, and road proofs to extensions." The freeze is executed here as a **closed inventory at construct-family level** (§1.2), an **explicit deferral register** (§1.3), and a **constraints-inherited register** (§1.4). The reviewer's conclusion states the intent this freeze implements: "The next iteration should reduce scope, define the core relation exactly, and make every example mechanically checkable."

The closure rule is default-deny under the {% include term.html id="no-implicit-rule" text="No Implicit Rule" %} discipline: **any construct not listed in §1.2 is out of the core**, and any construct listed in §1.3 is out of the core even if a v0.2 opcode table carried it. A construct enters or leaves the inventory only by an amendment to the repair sequence, adjudicated under the {% include term.html id="boc-policy" text="BOC policy" %} with the Loop-2 transcript as the binding constraint source. The freeze states **boundaries, not semantics**: per-construct state transitions, encodings, token lifecycle algebra, and failure behavior are Step-2 deliverables and are deliberately not pre-empted here. Where a §1.2 row names a semantic obligation, it records the obligation's owner step; it does not discharge it.

## 2. Operational Semantics (Repair Step 2)

This section discharges the second step of the repair sequence on the byte-unchanged freeze of §1. The operative instruction is the Step-2 row of the sequence, preserved verbatim: action — "Publish operational semantics"; acceptance condition — "Typed configurations, small-step transitions, block arguments, dynamic instances, token lifecycle, failure behavior, and deterministic encodings. State determinism as `Eval(Intent, D, V) = Execution` with all semantic versions explicit." The inheritance register that headed this step in the forward map is fixed input and is preserved here verbatim so that the map of §3 can retire the row without losing it: "The nine-family inventory as the closed construct set; the F3 block-argument model; the Obj 5/`QO-22` lifecycle surface; the F5 transition-record obligation list; the fixed-width/exact reconciliation (§1.4)." Each register item is consumed at a named subsection (§2.2, §2.4, §2.5, §2.6, §2.7), and none is re-adjudicated: the registers of §1 bind this section as written, and the semantics defines the machine over them rather than around them.

Two declaration disciplines govern every choice below. First, the default-deny closure rule of §1.1 carries into semantics unchanged: only the nine frozen families receive transition rules, and a construct of a deferred family is not a runtime trap but a statically illegal program (§2.3). Second, every policy choice this section makes — the reconciliation stance of §2.7, the terminal-wins rule of §2.5, the clock advance rule, the encoding layout of §2.6 — is declared explicitly and binds under the semantics version of §2.1; under the {% include term.html id="no-implicit-rule" text="No Implicit Rule" %} discipline, nothing in the transition relation is resolved by silence, convention, or implementation accident.

### 2.1 The Determinism Statement

The determinism claim of this section is stated exactly as the acceptance condition requires:

> **`Eval(Intent, D, V) = Execution`** — for every well-formed triple `(Intent, D, V)`, evaluation yields exactly one execution.

The triple is bound as follows. **Intent** is the program artifact: the typed block graph with its block-argument signature (§2.4), the instruction sequence of each block over the nine frozen families, the declared type bound of every value, the declared fallback edge of every lookup (§2.5), the extension side table for non-uniform per-instruction attributes (§2.6), and the profile reference carrying the declared trip/depth ceilings and type-bound parameters. Intent is *well-formed* iff it satisfies the static legality rules of §2.3–§2.6: only core-family instructions; an arity-closed, consistently typed block-argument graph; every value carrying a declared type with a declared bound; every lookup carrying its declared fallback edge; every flag combination known and every `EXT` side-table reference resolving; and a profile reference present, since ceilings and bounds are profile parameters (Obj 2). A program that mentions a deferred family, carries an unknown flag combination, or cites a nonexistent side-table record is not a legal Intent and has no semantics — rejection is static, at Intent formation. **D** is the dependency environment: the content-addressed input environment (constant-table entries and input values, each cited by content address) that execution may read, under {% include term.html id="dependencies-determinism" text="dependencies determinism" %}; execution reads no input that Intent does not declare. **V** is the explicit version tuple `(semantics version, encoding version, profile version)`: the semantics version is this file's version — v0.3.0-draft.2 pins the transition relation, the lifecycle algebra, and the terminal-wins rule of this §2; the encoding version pins the layout of §2.6; the profile version pins the declared ceilings and bounds that ride Intent. Versions are part of the determinism claim, not metadata about it: a change to any component of `V` is a different `Eval`, and the transition record of §2.6 binds all three into every committed transition.

**Execution** is the maximal transition sequence from the initial configuration under the relation of §2.3, together with the complete ordered list of transition records and the terminal configuration. The initial configuration is declared, not computed: entry block with its arguments bound from `D`, empty status pool and receipt queue, zero accumulators, zero clock, step index 0, state running, version bindings `V`. The semantics makes no universal termination claim: bounded loops carry declared ceilings, but whether a given Intent terminates within them — and how budget admission certifies that statically — is the Step-3 deliverable (F4). The claim this section makes is weaker and exact: *if* a well-formed triple's evaluation reaches halt, the halt is reached by exactly one transition sequence, and that sequence is fully recorded.

### 2.2 Typed Configurations

A **configuration** is the typed state tuple below. Every component is finite at every step, every component is encoded by the canonical encoding of §2.6, and every component cites the register item that binds it.

| Component | Content | Binding |

Work quantities are measured in the {% include term.html id="compute-unit-u" text="Abstract Compute Unit U" %} under the declared envelopes of the {% include term.html id="simemp" text="SIMEMP" %} constraints, as in §1; no work value is *computed* by this semantics — the accumulators are updated by transition rules whose charges are declared quantities, and the ledger equation that makes them sound is Step 3's deliverable, not this section's.

Two identity disciplines separate what §1 froze. **SSA name identity** is the pair `(static value id, instance id)`: two instances of one static id are distinct names, and no transition ever overwrites a bound name — redefinition is represented by minting a fresh instance (§2.4). **Denotational value identity** is equality of full canonical encodings under minimal-zoom normalization for zoom-carrying values (`QO-24`): a tuple equals another tuple only by full canonical encoding, never by header or hash equality (F6), and the zoom history of a value is not part of the value — it rides the artifact-lineage record whose commitment is Step 5's. The normalizer of comparison (§2.3, family 4) is declared deterministic in this semantics; the proof that its minimal representation is unique at every lattice boundary is a named demonstration obligation carried to the promotion artifacts, recorded here rather than silently assumed.

### 2.3 The Small-Step Transition Relation

The transition relation `C → C'` executes exactly one instruction per step, and it is a partial function: for every configuration `C` at most one successor `C'` exists. The core has no scheduling freedom to abstract away — branch conditions are exact predicates (family 4), the token lifecycle of §2.5 declares its own tie-breaks, and the terminal-wins rule is lexicographic — so determinism is a property of the declared rules, not of an implementation's discipline. The rule inventory below covers the nine frozen families and nothing else; it is the closed set of §1.2 restated as dynamics.

| Family | Transition rule (declared) | Binding |
|---|---|---|
| Constants | A constant reference binds the content-addressed constant's canonical value to a fresh or declared `(static value id, instance id)` in the store. If the value exceeds its declared type bound, the transition is a typed rejection before dispatch (§2.5), never a wrap or truncation | family 1; Obj 2; F1 |
| Tuples | Tuple construction produces the canonical encoding over exact component values; equality and ordering tests compare full canonical encodings | family 2; F6 |
| Exact arithmetic | Integer operations over exact values within declared operand bounds; operands are checked against their declared bounds at dispatch, before the operation executes; a result exceeding its declared result-type bound is a typed rejection at the same transition | family 3; F1; Obj 2 |
| Comparison | Equality and ordering predicates over canonical exact values, under the declared deterministic minimal-zoom normalizer for zoom-carrying values; behavior at declared zoom boundaries is part of the declared function | family 4; `QO-24` |
| Bounded structured control | A branch supplies the target block's argument values and control transfers with fresh instances minted at block entry (§2.4); loop back-edges are ordinary block edges; exhausting a declared trip/depth ceiling is a typed failure (§2.5), never silent unrolling; the F4 admission rule is Step 3's | family 5; F3; F4 |
| Status | Births, observations, consumptions, propagations, and terminalizations follow the lifecycle algebra of §2.5; the only semantic mappings in the core are the declared ones of that section | family 6; Obj 5; `QO-22` |
| Commit | Every transition emits exactly one transition record — the F5 field list under the deterministic domain-separated encoding of §2.6; equal records denote equal transitions, and equal record sequences denote equal executions | family 7; F5 |
| Witness | Witness and receipt emission appends to the receipt-order queue in emission order; the order is total in the sequential core | family 8; F3 |
| Halt | The halt transition terminalizes every outstanding token (§2.5), emits the terminal receipt, and sets `halted(outcome)`; a fatal token halts immediately at the transition that births it, and a later halt instruction cannot re-seal or overwrite a fatal state | family 9; F7 |

**Extension boundary.** A construct of a deferred family — calls, saturation, containers, fork–join, road-proof discharge — has no transition rule, and a program containing one is statically illegal at Intent formation (§2.1). This is the §1.1 closure rule carried into dynamics: the boundary is a specification statement, not an extension specification, and the validator that enforces it mechanically is a Step-4 artifact.

### 2.4 Block Arguments and Dynamic Instances (F3 Discharged)

Control is frozen as basic blocks with explicit block arguments, and the dynamics make the v0.2 defect impossible by construction. Every edge of the block graph — forward, branch, and back-edge — supplies operand values for exactly the target block's declared arguments, and entering a block mints a fresh instance id for each of its arguments. Loop headers therefore take their per-iteration state as block arguments, and a back-edge operand **may occur later in the static instruction order than the branch that cites it**: the operand is resolved when the edge executes, at block entry, not at static scan. This is precisely the named defect of F3 — "loop headers need block arguments whose back-edge operands may occur later statically" — discharged as a static well-formedness rule (the block-argument graph is arity-closed: every edge supplies the target's arity, typed consistently) plus an entry-time resolution rule (§2.3, control row).

Within a block, each instruction that defines a value binds it in the current instance context, so one value per static instruction is a statement about *names* — the pair `(static value id, instance id)` — and never about storage slots: per-iteration redefinition mints a new instance instead of overwriting an old one. Instance ids are minted in transition order, are execution-scoped, and are never reused within an execution, which makes the dynamic value store's canonical encoding (§2.6) well-defined at every step. The store is the abstract semantic state; what a profile does with it — liveness windows, register allocation, spilling under `QO-18` — is realization, not semantics: no capacity constant of any profile is a validity limit of this relation (Obj 2).

### 2.5 The Token Lifecycle Algebra and Failure Behavior (Obj 5 / `QO-22` Discharged)

The review's verdict on `QO-22` is preserved as the design constraint: "The two-tier token idea is sound; the v0.2 partition and mappings are not." This section therefore declares the v0.3 partition, the lifecycle verbs over it, and the failure behavior of the core, with no silent mapping anywhere.

**The two tiers.** **Tier O — operational tokens** are recoverable by specified fallback behavior and carry no semantic verdict. Declared member: `STATUS_LOOKUP_MISS` — operational control flow, consumed by the declared recompute fallback: the fallback edge is declared in Intent (§2.1), a lookup miss routes control to that edge's target, and the token is consumed when the fallback block completes; repeated misses re-birth the token with a fresh birth site, and every birth and consumption is traced. **Tier S — semantic tokens** are outcomes that propagate to the exit unless the program explicitly consumes or promotes them. Declared members: `STATUS_NEG_EVEN_ROOT` — maps to `NO_SOLUTION` in the real frame if and only if the program explicitly promotes the frame by a declared typed instruction, and never otherwise; and `EXPRESSION_TOO_COMPLEX` — the resource/representation-limit token, born by the typed rejections of §2.3 (a value exceeding its declared bound before dispatch, an exhausted declared trip/depth ceiling).

**Lifecycle verbs.** Birth (typed, sited at `(step index, position)`), observation (a typed predicate that reads a token's presence and consumes nothing), consumption (only by the declared fallback of Tier O or an explicit program instruction), propagation (unconsumed tokens ride the pool across transitions unchanged), and terminalization (at halt, every outstanding token terminalizes and is recorded in the terminal receipt — unresolved semantic debt at every exit is surfaced, never discarded, which is the family-9 scope boundary of §1.2). The `QO-22` test list — success-after-recovery, unresolved debt at every exit, multiple outstanding tokens — passes to Step 4 as the conformance suite's input, unchanged.

**Failure behavior and the terminal-wins rule.** A typed rejection is fatal: the machine cannot proceed past a rejected instruction, the transition that births the fatal token is the final transition, and the fatal state is sealed in that transition's own record — a later halt instruction cannot re-seal it (F7). The terminal-wins rule, which `QO-22` requires to be specified, is declared as follows and is total: fatal tokens outrank all non-fatal outcomes; among multiple fatal tokens, the earliest birth wins, ordered by `(step index, tier, declared type id)` lexicographically; with no fatal token outstanding, the outcome is the program's halt outcome, with every outstanding non-fatal token terminalized and recorded as unresolved debt in the terminal receipt. At most one fatal token can be outstanding at any halt, because a fatal birth is itself immediately terminal — the lexicographic tie-break is declared anyway so that the rule is total without case analysis on how halt was reached. Exactly one outcome is produced, every outstanding token appears in the terminal record, and the rule's tie-breaks are declared: determinism by construction, not by silence. The named wrong mappings of Obj 5 stay named and excluded — a lookup miss is not an epistemic defect, a negative even root is not complexity evidence, and no token-consuming behavior is left implicit.

### 2.6 Deterministic Encodings and the Transition Record (`QO-30` / F5 / F6, Step-2 Share)

**Words and values.** The 64-bit word is preserved as the transport unit (`QO-30`), and the reconciliation of §2.7 fixes what that preserves: the word is a transport and commitment unit, not a value-semantics width. An exact value encodes as its declared type tag, a word-length prefix, and the minimal big-endian sequence of 64-bit magnitude words under a declared sign convention — no leading zero words, one canonical zero — so each value has exactly one encoding. Per-instruction attributes that are not uniform across the program ride the `EXT`-flag pattern: the flag indexes a canonical header extension record in the side table carried by Intent (`QO-30`), and an unknown flag combination or a dangling side-table reference makes the Intent statically illegal (§2.1); the validator that enforces this mechanically is Step 4's.

**The transition record.** Every transition commits the F5 field list, preserved verbatim from the family-7 row of §1.2: prev root, program root, step index, PC, decoded word or its hash, input/output IDs, pre/post state roots, work charged/refunded, clock, status, {% include term.html id="receipt" text="receipt" %} IDs, semantics/profile versions. The record is encoded deterministically and domain-separated — each field under a declared domain tag, in the declared field order, under the deterministic-encoding discipline of CBOR (RFC 8949), which is the review's own encoding reference [4] — so that equal records are byte-equal records. Pre/post state roots presuppose a canonical configuration encoding: the value store encodes in `(static value id, instance id)` order, the token pool in `(birth step index, type id)` order, the receipt queue in emission order, every component through the value encoding above. The state-root function is named by the encoding version — the concrete hash is an encoding-version parameter whose implementation artifacts belong to the Step-4 oracle — and its determinism follows from the canonical encoding, which is what F5's discharge needs at this step: equal commitments denote equal executions, single-transition records here, full-trace roots in Step 5.

**Comparison and collision surface.** Tuple equality is full-canonical-encoding equality (F6) — never header equality, never hash-as-identity. The collision bucket of complete artifacts and the quarantine-on-genuine-collision discipline are Step 5's artifact-comparison commitments (per the F6 row of §1.4); what Step 2 freezes is the equality rule the bucket will compare under.

### 2.7 The Fixed-Width/Exact Reconciliation (Named Obligation Discharged)

The tension is recorded in §1.4 and is resolved here by declaration, as the register requires: `docs/abstractionLayers.md` §6.3 and §13 describe the QnIR execution handler as "a small, fixed-width deterministic machine over integer arithmetic, with bounded loops and no floating point," while the frozen core names *exact arithmetic*. The declared stance of this semantics version is **exact value semantics over a fixed-width transport**:

1. **Values are exact.** Integer values are exact integers of unbounded range at the semantic layer; no operation wraps, saturates, or truncates, and no value is ever silently mapped (Obj 5).
2. **The transport is fixed-width.** The 64-bit word is the unit of encoding, dispatch, and commitment (`QO-30` preserved); an exact value occupies a minimal-length word sequence (§2.6), so the machine is exactly the "small, fixed-width deterministic machine" of §6.3 — fixed in its word format, not in a value-width limit.
3. **Finiteness enters only by declaration.** Every value carries a declared type bound, and bounds are profile parameters, never core validity limits (Obj 2; `QO-18`); there is no universal capacity constant anywhere in the relation.
4. **Exceedance is typed, before dispatch.** A value exceeding its declared bound is rejected before dispatch as a typed failure (§2.3, §2.5) — surfaced as `EXPRESSION_TOO_COMPLEX`, traced in the transition record, never absorbed.

The alternative stance — fixed-width 64-bit value semantics with typed overflow — was rejected on the register's own grounds: it would make a 64-bit capacity constant a core validity limit, which Obj 2 forbids in the absence of evidence, whereas the exact-over-transport stance requires no capacity constant at all. The choice is thereby forced by the constraints register rather than preferred by taste, which is the only form of resolution this program admits.

**Recorded reading note (no cross-file mutation).** Under the declared stance, §6.3's "fixed-width" is read as the transport and word-format width, not a value-semantics width. `docs/abstractionLayers.md` is not edited by this draft (one file at a time; the §13 open item stays *in progress* through this file); if the portal later aligns §6.3's wording, that is a future bookkeeping wave. This note is the record of the reading: the reconciliation is discharged by declaration here, together with the Obj 2 overflow stance and `QO-30` word-format preservation, exactly as §1.4 required — not by silent rewording of a canon file.
